# Validation record

Initially validated on Windows x64 on 2026-10-23, using Node.js 24.13.0, Rust stable MSVC 1.99.1, and WebView2 155.0.4283.62. Selected-sensor and common-visibility checks were added on 2026-10-27.

| Check                           | Scope                                                                                                                                |
| ------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------ |
| `npm run build`                 | TypeScript strict checks and production Vite bundle                                                                                  |
| `npm test`                      | 57 unit tests, including STL binary/ASCII validation, unit defaults/relink, reference frames, unique names and visibility geometry   |
| `npm run test:e2e`              | 23 Chromium flows including STL/STEP metric import, occlusion/relink/cancel, reference editing/export preview, gizmos and visibility |
| `npm audit`                     | No known npm dependency vulnerabilities at validation time                                                                           |
| `npm run tauri build`           | Native Windows release executable and x64 NSIS installer                                                                             |

| `npm run test:native-close`     | Native close regression: clean exit, cancel discard preserving edits, confirmed discard exiting without a browser unload prompt      |

The native smoke script connects to an explicitly launched test app at CDP port 9223. This port is not enabled by the app itself, the installer, or normal launch. It is supplied only by the test launch environment (`WEBVIEW2_ADDITIONAL_BROWSER_ARGUMENTS=--remote-debugging-port=9223`).

STL/STEP import (2026-10-27): original 1000 × 2000 × 3000 mm calibration blocks import at 1 × 2 × 3 m. Browser tests verify both formats, STL unit changes, sensor first-hit distance at 1.350 m, saved alignment relink, failed STEP preservation and worker cancellation. Unit tests cover ASCII/binary STL, non-finite/truncated inputs and history. `scripts/native-cad-smoke.mjs` verifies the release WebView2 app's real local WASM/worker/CSP, units, pose editing and occlusion; only dialog/file-read transport responses are substituted. Actual native file-dialog interaction remains manual. Native screenshots are `screenshots/import-stl.png` and `screenshots/import-step.png`. One full-suite boundary test was interrupted by a development-page navigation; its isolated rerun passed. The other 22 flows passed in the full run.

Browser tests exercise real file uploads/downloads. Native open/save dialog interaction and a fresh-machine installer run have not been automated. Native capabilities are compile-validated; filesystem scope is extended by Tauri's official dialog plugin only for selected files. No wildcard filesystem scope is granted.

The native close regression launches its own app processes with test-only CDP ports 9224/9225. It calls the native window close command, which emits the same `CloseRequested` event as the title-bar X, and verifies process termination. Dirty-state cases stub only the confirmation dialog answer; the native close event, SDK window destruction, and ACL enforcement remain real. `--expect-blocked` reproduced the original missing-destroy-permission failure before rebuilding. The fix grants `core:window:allow-destroy`, accepts the original close request after confirmation, and reserves the browser unload prompt for browser mode.

Occlusion preview added on 2026-10-25 and changed to per-fragment mesh visibility on 2026-10-26. Unit tests verify first surface wins, back-face/inside hits, hidden blocker exclusion, non-uniform/tiny scales, instancing, pre-near blocking, camera planes, 360-degree LiDAR, ground clipping and immutable world-space triangle snapshots. Browser tests verify sampled diagnostic distances against known wall and GLB dimensions. GPU regressions render into real WebGL targets and read pixel alpha: a thin blocker deliberately missed by every old camera sample must discard its shadow pixel while leaving adjacent pixels visible; first-contact overlays must respect FOV limits and blockers before the near plane. Shader compilation errors fail the thin-blocker test. `screenshots/occlusion-wall.png` shows visibility stopped at a wall. The display is limited by mesh, screen and floating-point precision; diagnostics remain sampled and no exact continuous-volume or coverage calculation is provided.

The initial per-fragment display omitted shadow side surfaces and showed crate-top speckles from unstable coplanar self-intersection. The follow-up adds silhouette-extruded side planes and plane-based receiver checks. GPU regressions now verify that side-on shadow pixels are present, a nearer overlapping shadow removes internal side surfaces, and a top surface at the demo sensor's exact 1.1 m height remains uncolored without speckles. Raising the sensor by 1 mm must give the same filled receiver pixels as a non-grazing reference. `screenshots/shadow-boundary.png` reproduces the reported bollard coordinates and an oblique front view. These tests supplement the prior far-shell pixel checks, which did not detect the missing volume sides.

Adding boundary passes initially made the software-rendered demo flow exceed its 45-second test timeout. Switching to demand rendering removed continuous idle BVH work; the same editor flow then completed in about 3 seconds without increasing its timeout. Orbit/gizmo interactions and uniform-only edits continue to invalidate the canvas.

The subsequent missing/notched-boundary report exposed a blocker-collection bug: Drei `Edges` uses `LineSegments2`, which extends `Mesh`. Its screen-space stroke template was incorrectly collected as opaque world-space triangles under tagged obstacles and rover parts. Collection now explicitly excludes these strokes. The regression uses the real `LineSegments2` hierarchy, checks both CPU and GPU snapshots, and compares all 16,384 camera far-plane pixels against independent analytic box/ground intersections with an outline attached. A second GPU regression renders complete camera/LiDAR boundaries around a box and cylinder from front, side, top and oblique views; adding display outlines must change zero pixels in all eight comparisons. Earlier bare-box fixtures did not reproduce the application's decorated meshes and missed this bug. Native screenshots `shadow-boundary.png`, `shadow-top.png` and `shadow-side.png` were captured with the reported bollard coordinates after this fix.

No remote repository was created and no release was published. The committed workflow prepares build artifacts when this project is pushed to GitHub.

Rotation controls (2026-10-27): Both move arrows and XYZ rotation rings are displayed by default. Ring radius is half the origin-to-arrow-tip length, checked against transformed geometry vertices. Pointer arbitration allows only one tool to drag at a time. Two browser regressions drag all three real rotation rings for a camera and a LiDAR with both controls visible. The fixture reads the rendered pick geometry to locate each ring, then uses actual mouse events; it does not set poses or invoke control callbacks. Each drag changes only the intended world-axis quaternion component from the initial pose, keeps position unchanged, adds one history entry, and is restored by one Undo. W/E solo-mode switching is also checked. These input tests disable BVH shading to avoid software GPU costs; separate GPU regressions cover visibility rendering.

Selected-sensor comparison (2026-10-27): GPU color readback distinguishes shared visible receiver points from points visible to only one sensor, screen-projected overlap with disjoint depth ranges, and points excluded by a third selected sensor. Coincident sensors retain their common surface; a blocker visible only from the second origin removes common coloring even when it lies before that sensor's near plane. Occlusion OFF and hidden-blocker cases restore the geometric common color. Mixed camera/LiDAR and rotated-away poses are also checked. Editor tests cover multiple selection, focusing FOVs, editing without losing the comparison, hidden-sensor exclusion and empty selections. Store tests verify that display changes leave saved scene data/history untouched and that removed IDs and loaded studies are handled.

Blind-spot highlighting uses the same GPU visibility decisions with a red hatched display mode. Pixel regressions verify red occluded receivers and unchanged visible colors for camera and LiDAR, including an occluder before the near range; FOV-exterior pixels stay clear. Disabling highlighting restores discarded shadows, zero opacity stays transparent, and hiding the blocker restores the visible color. An editor regression verifies the default-on toggle, idle canvas redraw, interaction with occlusion OFF, and no changes to scene data or undo history. `screenshots/blind-spots.png` shows the default view.
